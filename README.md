# ПО БАРТЕРУ

Публичный сайт: https://po-barteru.onrender.com  
Репозиторий: https://github.com/Nakarp2023/po-barteru

## Архитектура

- Frontend: `index.html` — HTML, CSS и JavaScript.
- Backend/data: Supabase (PostgreSQL, Auth, RLS, RPC и триггеры).
- Hosting: Render Static Site; деплой выполняется из ветки `main`.
- Платные функции используют серверные записи заказов и подтверждение оплаты; нельзя менять статусы платежей из браузерного кода.

## Важно: не применять начальную схему к production

Файл `supabase/schema.sql` — начальная схема для создания нового пустого проекта, а не актуальный полный снимок production-базы. Не запускайте его повторно в существующем Supabase-проекте как способ обновления схемы.

В production уже применено больше миграций, чем сейчас представлено отдельными SQL-файлами в `supabase/migrations/`. Историю миграций и структуру production необходимо согласовать перед использованием Supabase CLI для автоматического применения миграций.

**До завершения сверки не запускайте `supabase db push`, не выполняйте массовый повторный запуск SQL из `schema.sql` и не удаляйте миграции, которые кажутся неиспользуемыми.** Сначала восстановите полный воспроизводимый набор миграций и сравните его с production.

### История миграций: восстановленные расхождения

Production Supabase содержит 87 записей истории миграций, а в репозитории пока хранится существенно меньше отдельных SQL-файлов. В ходе аудита точные SQL-операторы для двух ранее сгруппированных файлов были восстановлены из `supabase_migrations.schema_migrations.statements` и разделены на файлы с исходными версиями. Эти файлы описывают уже применённую историю; их не нужно повторно запускать в production.

- Лимит активных объявлений восстановлен как две миграции: `20261027071751_enforce_active_listing_plan_limits.sql` (функция и триггер) и `20261027071839_serialize_active_listing_limit_checks.sql` (добавление транзакционной блокировки для сериализации параллельных проверок).
- Статусы прочтения и доставки сообщений восстановлены как три миграции: `20261027113823_add_message_read_receipts.sql`, `20261027114216_add_persisted_message_delivery_status.sql` и `20261027114255_enforce_server_message_delivery_timestamp.sql`.

Это устраняет именно два известных расхождения группировки, но **не означает, что все 87 production-миграций уже представлены в GitHub**. Перед использованием Supabase CLI всё ещё нужна полная сверка оставшейся истории. Новые миграции, добавленные в production в рамках аудита, должны храниться в GitHub с точным префиксом версии из `supabase_migrations.schema_migrations`. При восстановлении старой истории не изменяйте production и не повторяйте уже применённый SQL.

## Правила безопасных изменений

1. Все изменения кода оформлять в отдельной ветке и Pull Request.
2. Изменения БД сначала описывать отдельной миграцией; не изменять данные платежей и статусы обменов без отдельной проверки и обоснования.
3. Для RPC с `SECURITY DEFINER` проверять `auth.uid()`, права участника и допустимость перехода состояния. Не снимать `SECURITY DEFINER` или `EXECUTE` автоматически: некоторые функции обслуживают доверенные транзакционные операции.
4. Не добавлять `service_role` key и другие секреты в браузерный код.
5. После слияния проверять статус деплоя Render и синтаксис JavaScript. Отдельно проводить ручную проверку ключевых сценариев на мобильном устройстве.

## Известные пункты аудита

- В Supabase Advisor отмечено, что защита от скомпрометированных паролей выключена; включение требует проверки настройки Authentication в панели Supabase.
- Advisor предупреждает о нескольких доступных авторизованным пользователям RPC с `SECURITY DEFINER`. Перед изменением проверять тело каждой функции и подтверждённые клиентские вызовы.
- Неиспользуемые индексы не удалять только на основании текущей статистики: проект молодой, и статистика использования может быть неполной.
